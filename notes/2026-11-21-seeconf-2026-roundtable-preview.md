## 一、核心命题

这是一篇**会前关注**，不是会后复盘。公众号原文是圆桌预热：SEE Conf 2026 定在 2026-11-28（周六），地点杭州·蚂蚁 A 空间，官网 [seeconf.antgroup.com](https://seeconf.antgroup.com)。文章只推进了一层判断——模型能力的突破正在改变创造的成本和边界，接下来该问开发者：哪些此前满足不了的需求，终于可以做成产品。圆桌题目是「创造的边界，应用的未来」，主持人程劭非（Winter）。

原文没有技术深挖，没有嘉宾观点，也没有可引用的架构或数据。场次、讲者和议题都出自官网日程，不出自这篇推文。

对这个仓库，要带着的问题是：**生成变便宜之后，哪些未满足的需求真能变成产品，前端和 Agent 体验靠什么撑住。**

## 三、底层逻辑

推文和官网日程说的是同一句的两面：模型把创造的成本打下来了，**便宜的生成不会自动变成好体验**。官网日程把这句说得更硬：生成很多，并不等于创造繁荣；技术突破也不会自动变成好体验。

成本下降之后，变稀缺的是三件事：

1. **验证**。做出来的东西是不是被需要，改完是否仍然有效。没有度量，「终于能做成产品」只是口号。
2. **交互契约**。同样的用户动作，应对上可预期的可见结果和副作用。生成式 UI 若每次长得不一样，就只是一次性出品。
3. **交付标准**。什么情况可以自动继续，什么情况必须停下来等人。标准进不了系统和界面，就只能靠模型当场发挥。

这和 [大 Agent 时代的验证工程](./2026-11-19-dagent-verification-engineering.md) 同向：生成越快，越难证明改出来的东西仍然有效。那场的指标、契约、灰度和状态机熔断，这里只当作听苏杰和圆桌的对照尺，不套到还没发生的演讲上。

## 四、对前端 / AI 产品前端的指导

下面是会前动作：看什么、问什么、回来和哪篇笔记对。演讲尚未发生，这里不写成已证实的做法。

### 4.1 生成式 UI：映射到 canvas ↔ agent 回路

竹光这场的官网日程集中在自然语言交互、生成式 UI，以及生成式渲染仍在演进。现场不要只记下「支持自然语言」。把议题映射到一条 canvas ↔ agent 回路，看它闭不闭合：

- **选区进 Agent。** 用户在画布上圈定一块界面、一段文案或一个组件时，这次选择是否作为结构化输入交给 Agent（节点、约束、已有样式），还是只剩对话框里的一句自然语言。
- **Agent 画回来。** 生成结果是否落回同一块画布，可继续改、可撤销；还是一块不能再编辑的截图或一次性 DOM。
- **自然语言和直接操作谁还在。** 改一个间距，是必须再打一句提示词，还是拖拽和属性面板仍然有效。自然语言若盖掉直接操作，原有的交互契约会被拆掉。

按这三拍记。会后若要收到自己的前端里，验收是：同一次选择重复跑，可见结果和副作用还能不能对上。

### 4.2 端云 Agent 与云沙箱：对照本地编码 Agent 和远程控制

同一场官网日程还写了跨设备、端云协同的 Agent 架构，以及云沙箱 AI 基建。映射到本仓库的问题是：本地编码 Agent 改仓库、跑命令，远端做重活或隔离执行时，控制面放在哪。

现场只记四件事，缺的就留空，不替讲者补架构：

- 哪些步骤在端上，哪些必须上云。切换条件是模型能力、数据能否出端，还是延迟。
- 云沙箱隔离的是什么：文件系统、网络、密钥，还是只是一个远程容器。隔离边界决定界面要不要做「即将执行」的确认。
- 跨设备时状态以谁为准。手机上确认、电脑上执行，或反过来，冲突了听谁的。
- 失败时用户看见什么。沙箱超时、端云断开，界面是静默重试，还是停在可恢复的一步。

算力可以放在云沙箱。改动的确认和回滚留在本地这一侧，留在用户看得到的界面上。

### 4.3 圆桌问题：会前写好，会上只追问

推文在征集观众问题。下面三问对着优先的三位嘉宾，并且都能落到交互、测试或发布。

1. **问终端侧（老郭，并接着竹光场的上下文）：生成式 UI 怎样才不是一次性出品。** 交互契约怎么定——同样的选择和约束，可见结果和副作用要一致到什么程度。视觉回归怎么跑——结果每版都在变，基线是截图、结构，还是行为。没有契约和回归，生成式界面无法做灰度，也无法验收。
2. **问元彦：Personal Agent 需要用户确认时，怎么打断、怎么熔断。** 哪些副作用（写文件、发包、部署）必须先展示「将要做什么」再放行。打断之后任务是挂起可恢复，还是直接失败。熔断条件写在产品状态机里，还是写在提示词里。对照验证工程笔记：停止条件进系统，不进 Prompt。
3. **问老郭，并用臻儿的产品场景追问：端侧部署和模型分级路由在客户端怎么选。** 什么请求留在端上，什么升级到云端大模型。路由失败或超时是否降级，界面是否标明当前档位。端上能力不足时，入口是隐藏还是禁用并说明原因。

玉伯和阴明接苏杰的题：创造变容易之后，工具和个人开发者用什么标准决定「这个不做」。

### 4.4 用苏杰这场对照验证工程笔记

苏杰的题目是「人人都能做产品了？然后呢？」。官网日程的四个切口——是不是真被需要、风险 / 瓶颈 / 流程怎么变、个人生产力不等于组织增长、竞争力还剩什么——会前就画成对照表，对着 [验证工程笔记](./2026-11-19-dagent-verification-engineering.md) 听。讲到的格子记下原话，没讲到的留空。

| 官网日程里的切口 | 对照笔记里已有的手段 | 现场要记下的 |
| --- | --- | --- |
| 做出来的东西算不算被需要 | 指标先行：完成率、打断率、二次追问率；对话轮次和停留时长会失真 | 他给的是可量化口径，还是体感 |
| 上线风险与流程 | 交互契约、视觉回归、影子流量 | 生成变容易之后，发布是把验证补厚，还是把流程改松 |
| 瓶颈从生产转到别处 | 灰度切流；验证周期受业务周期约束 | 他是否把「能做出来」和「敢切到真实流量」分开 |
| 个人变快，组织未必变好 | 状态机熔断、副作用确认闸门 | 个人 Agent 的刹车和组织级发布标准是不是同一套 |

会后复盘只填他实际说了的格子。空格子也是结论：这场没有给出工程手段，交付标准仍以那篇笔记为准。
