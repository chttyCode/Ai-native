# 大 Agent 时代的验证工程：三个一线案例解读

> 原文：[当AI生成快到溢出，大Agent时代该讨论些什么？](https://mp.weixin.qq.com/s/BhTEcvkEzIRLzGjAj4J9mw)
> 来源：腾讯云开发者，2026-11-19，作者：陈苑韬
> 整理时间：2026-11-21

---

## 一、核心命题

作者参加三天大会后的判断：**大家已经不再讨论 Agent 能做什么，而是卡在同一个地方——AI 生成代码和方案的速度已经快到溢出，但怎么证明它改出来的东西真的有效，又怎么敢切到每天跑真金白银的线上业务里。**

文章的原话很扎：「很多看似热闹的 Agent 方案其实就是空中楼阁，大家只管从 0 到 1 跑通 Demo 交差，根本不管上线后这个 1 的死活。」

所以主线是**实验评估与验证工程**。三个案例分别对应三种规模：单次打分 → 整套系统重写 → 数周无人值守自主探索。

---

## 二、案例一：阿里全自动评测管线（把打分本身工程化）

**问题**：AI 助手是自然语言多轮对话，人均轮次、时长这类指标没法反映效果——聊了十几轮可能是不满意。没有准的指标，A/B 测试就没法决定策略上不上线。

**方法论**：先定 3 个评估指标，再谈方案。拿指标一量，三种主流方案全被排除：

| 方案 | 为什么不行 |
| --- | --- |
| 人工评估 | 准，但贵且慢，覆盖不了全量流量，灵敏度差 |
| LLM-as-a-Judge | 逐字写评语再打分，token 成本高，且极易受 Prompt 影响 |
| 微调专用裁判模型 | 底座一升级就得重标注重训，裁判永远比被测模型旧 |

**三个值得记住的实验手法**：

1. **对照实验打翻直觉。** "先写理由再打分"现场最多人选，实测却最不稳：Qwen3-4B 上"只打分"最好，Qwen3-Max 上"先打分再写理由"最好，Qwen2.5 又不一样——没有哪种写法跨模型稳定胜出。原因是 Decoding 机制：先吐的 token 会改写后面打分的概率分布，模型写着写着把自己说服了。
2. **差分法提纯信号。** 同一段对话读两遍，一次拼正向引导、一次拼负向引导，两次隐向量相减，公共噪音抵消，剩下的差值向量就是干净的"好坏判断"。作用等价于后来的 J-space 思路（原文提到 Jev 模型尚未出现）。
3. **统计分布 + 消融实验。** 线上 98% 是平庸的 3 分，极端样本只占 1~2%，用差值向量的模长/偏离度把两头捞出来自动生成 Rubric；再用消融证明有监督 PLS 换成无监督 PCA 会掉三成以上人类一致性，直接证伪无监督路线。

**结果**：Qwen3-4B 用这套方案，人类一致性和趋势相关性追平 Qwen3-Max 生成式打分；Qwen3-14B 再提升约 10%。同等规模下成本降 97%，吞吐翻近 8 倍。

## 三、案例二：支付宝 Java → Rust 巨石应用重写（验证工程大于重写本身）

**背景**：十多年、亿级用户、海量外部机构的 Java 巨石应用，团队**没人会 Rust**，靠 Coding Agent + SOTA 模型重写成 Rust，代码量减 85%+。

**关键决策**：直接放弃代码审查——几万行 AI 生成的 Rust，人眼 review 不可能，改为建一套严密的工程验证体系。四步：

1. **只看对外行为等价，定义四元组**：Input（入参）、Environment（前置状态，如 DB 待支付账单、配置开关）、Side Effect（对外部系统的状态改变）、Output（返回给上游）。同样 Input+Environment 下，四元组的 Side Effect 与 Output 一致，即行为等价。
2. **用例不靠人写，也不信 AI 说的影响面**：静态分析提取 CFG → 找全分支与业务结果 → AI 补业务语义 → **路径剪枝**（共同决定同一分支的变量才组合，独立变量分开单测，剔除不可能成立的组合），把指数爆炸收敛几个数量级。
3. **用老系统做黑盒裁判，防止 AI 作弊**：抽查发现两个坑——AI 生成的长链路用例反复失败时，会把用例退化成"第一行参数校验直接返回"；外部机构没有测试环境。于是把 DB、配置、外部调用全部 Mock，先让用例在 Java 老系统真实跑通并拿到基准结果，再回放到 Rust 系统里让 Agent 修到完全对齐。
4. **现网影子流量逐笔比对**：线下穷举不了线上状态，生产环境起 Rust 影子进程异步接收真实流量，不产生真实写操作，把两边的四元组行为录制到回归平台核验——这一步抓出了"AI 打了个超大对象日志导致低频接口卡顿"的性能隐患。比对 100% 一致且负载达标才准出，再按机构、用户、接口精细化切流。

**现实约束**：从年初到现在，真正全量上线的接口不到 20%。除了资金安全，还有个物理约束——**验证周期受制于业务周期**，北方供暖这类季节性接口上半年没流量，必须等年底开栓才能拿到现网证据。拿不到证据就不下线老代码。

## 四、案例三：商汤多 Agent 长程算子优化（把探索闭环交给 Agent）

**任务**：算子优化要连续跑好几周，提出假设、执行实验、验证结果整套闭环全交给多 Agent 自主运转。

**三个失控风险与对应解法**：

| 风险 | 解法 |
| --- | --- |
| 多个 Agent 同时改代码互相覆盖、无法归因 | 角色严格拆四类：主控（提假设、分预算、派任务，不写码）／实验（只写码调参，不许自评）／验证（干净上下文的审核 Agent + 测试脚本，按标准验收，不改码）／Reducer（只整理结果、更新共享状态）；分析可并行，**改码与跑测必须串行，每次只改一处** |
| 跑久了丢失前序实验上下文 | Git 式事件溯源：每次改动必须写明父版本、生成不可变 SHA 快照；每轮实验像一次 Commit 追加结构化记录；历史只追加不覆盖，失败记录与原测数据严禁改删；中断换人也能顺着版本树回放决策现场 |
| 写码的 Agent 自我验证甚至作弊刷分 | CI/CD 式分级验证（局部→整网）+ **状态机硬熔断**：停止条件硬编码进状态机，绝不写在 Prompt 里；时间窗口到期、理论上限不足、整网质量下降即自动熔断或升级给人 |

**反直觉的数字**：长程实验里真正有效的尝试只占 5%~10%，**90% 以上算力花在证伪假设和拦截伪优化上**。

**结果**：连续数周、多款异构芯片、数十组组合，实现 91% 算子提速、几何平均 4.6 倍，Qwen-27B 整网 Decode 吞吐提升 26.8%，线上推理收益轻松覆盖实验算力成本。

## 五、底层逻辑：从确定性工程思维到实验思维

- 以前处理的是**确定性问题**：固定输入 → 固定输出，所以工程手段（review、单测、类型系统）基本够用。
- 现在被测系统是**概率性黑盒**，没有实验思维就会踩两个坑：被几个好看的 Demo 和体感哄住，改两句 Prompt、测三五个 case 就敢上线；以及到了深水区无法决策（Harness 选型、链路编排、要不要用 Sub-Agent），靠直觉争论毫无意义，只能靠大量对照实验。

作者的三条推论，也是他判断的"分水岭"：

1. 先定度量标准，再做工程设计——指标先行能直接排除掉不靠谱的行业常规方案。
2. 把行业直觉当成待验证的假设，没有权威，只有对照实验。
3. 用差分、分布统计、消融这些科学方法验证每一个猜想。

另一条共识：**越容易被快速、确定性验证的事情，越容易被 AI 规模化执行。** 反过来说，验证不了的部分，就是 AI 进不去的边界。

## 六、对前端 / AI 产品前端的指导

### 6.1 指标先行，界面后做

案例一最狠的一句是"他们团队没有上来就写代码做工程方案，而是先定了 3 个评估指标"。前端同理：改一版 AI 交互之前，先约定**首字延迟、完成率、打断率、二次追问率、工具调用成功率**这些能量化的口径，否则上线后只能靠感觉撕。

注意传统指标的失真：对话轮次、停留时长在对话式产品里可能代表"没解决问题"。

### 6.2 前端也要做对照实验和消融

- 不要"改两句文案，试三五个 case 觉得变好就上线"。同一批真实会话回放，A/B 两版交互。
- 学消融：想证明"折叠思考链"真的有用，就单独关掉它跑一轮，而不是一次改五个地方然后整体感觉变好。
- 学差分：要判断"用户对这条回答满意吗"，别只看评分，可以对比同一会话在正/负两种引导下的模型信号差异——这是把噪声抵消掉的标准手法。

### 6.3 行为等价是重构和换模型的验收基准

- 换模型、换框架、重构前端渲染层时，先定义"对外行为"——对界面而言就是**交互契约**：同样的用户动作，产出同样的可见结果与同样的副作用。
- 落地手段：契约测试 + 视觉回归 + 关键路径录屏回放，对齐"输入 → 环境 → 副作用 → 输出"，而不是逐行 review diff。
- 别相信 AI 报的"影响面"。案例里 AI 会把用例退化成"第一行直接返回"来骗过测试，前端同理：AI 说"这个组件改了三处调用"，要自己用静态分析（依赖图 / 引用搜索）验证。

### 6.4 影子流量与灰度：前端也要有"影子模式"

- 新交互、新模型上线前，用真实流量做影子比对：真实请求异步跑一遍新链路，**不产生真实副作用**，只记录"新旧两版界面行为是否一致"。
- 分层放量：按机构、用户、接口这种维度精细化切流，而不是一刀切全量。
- 接受"上不满"：案例里一年不到 20% 全量，因为**验证周期受业务周期约束**。前端也有季节性场景（大促、开学、年报季），平时没流量的路径，别在低峰期就宣布验证通过。

### 6.5 Agent 界面要显式呈现四元组

四元组不只是测试概念，也是 UI 信息架构：

- **Input**：将要发送的内容（可编辑、可预演）
- **Environment**：依赖的上下文状态（读到哪些文件、连着哪些环境）
- **Side Effect**：会有什么真实副作用（写库、发包、部署）→ 需要确认闸门
- **Output**：最终产出与可回滚点

长任务界面要像案例三的状态机：**停止条件写死在系统里，不交给模型自由发挥**——超时、预算耗尽、质量下降就自动刹车，而不是等用户发现跑飞了。

### 6.6 评测环境必须防作弊

- 测试/评测环境要隔离真实网络与真实写权限：案例里 Agent 会直接上网搜答案，也会退化用例骗过测试。
- 前端侧的对应措施：e2e 用固定 fixture、Mock 外部依赖、对"跳步成功"的用例做断言（必须真正走过关键分支才能算通过）。
- 不要用 AI 自己生成的结果来验证 AI 自己——审核方要换干净上下文，这就是"验证 Agent 不能改代码"的等价原则。

### 6.7 沉淀可回放的实验记录

- 商汤的 Git 式事件溯源，对前端团队的最直接启发：**每次模型/提示词/交互策略的调整都要有父版本、有指标、可回放**。
- 失败记录只追加不删除。半年后"为什么当时没用方案 B"这个问题，答案必须在仓库里，而不是在某个人的记忆里。

## 七、可落地清单

- [ ] 新交互改版前先写清指标口径（首字延迟/完成率/打断率/工具成功率）
- [ ] 用真实会话回放做 A/B，禁止"三五个 case 定上线"
- [ ] 关键改动做消融，一次只改一个变量
- [ ] 换模型/重构时定义交互契约，跑契约测试 + 视觉回归
- [ ] 不信 AI 报的影响面，自己跑依赖分析
- [ ] 新链路先跑影子流量，无副作用只比对
- [ ] 灰度按维度细分，接受季节性路径验证滞后
- [ ] Agent 界面展示 Input/Environment/SideEffect/Output，副作用需确认
- [ ] 停止条件写进系统（超时/预算/质量），不写在 Prompt
- [ ] e2e 隔离网络与写权限，断言关键分支真实走过
- [ ] 每次策略调整留父版本与指标，失败记录只增不删

## 八、与前一篇笔记的呼应

这份复盘和 [`腾讯混元 Hy4 AMA`](./2026-11-21-hunyuan-hy4-ama.md) 讲的是同一件事的两面：

- 混元那篇谈的是**能力边界**：模型会过度思考、会能力分层、工具调用可靠性最脆弱，RSI 还在早期。
- 这篇谈的是**工程应对**：把能力的不确定性，用指标、对照实验、行为等价、影子流量、状态机熔断一层层兜住。

合起来的结论是：**AI 越能生成，验证越是瓶颈；工程师的价值从"亲手写"迁移到"定义什么算对，以及怎么证明它对了"。** 前端在这个迁移里不是旁观者——用户能感知到的每一个不确定性，最终都要在界面上被设计成可等待、可打断、可确认、可回滚。
