## 一、文章速览

AMA 里真正有工程价值的结论，可以归成六条：

| 主题 | 团队原话要点 |
| --- | --- |
| 模型规模 | 下一代 Hy 参数会显著扩大，仍相信 Scaling Law；但"做得扎实的较小模型往往能胜过更大的模型，且成本更低" |
| 产品分层 | Hy4 主打通用智能与复杂任务；Hy4 flash 走低成本快响应，单任务成本约为 Hy4 的 1/20 |
| 最大短板 | 被问"后训练最难改善的行为"，答案是**过度思考**（CoT 过长） |
| RSI | 递归自我改进仍处早期，有内部基准，但当务之急是打牢基础智能 |
| 能力退化顺序 | 若压缩激活参数，最先掉的是**推理深度、长上下文跟踪、工具调用可靠性** |
| 真实任务 | 智能体编程 / PR 审查这类内部基准拿到满分（且速度最快），但明确"不刷榜"，老基准分数已饱和 |

技术侧的三个关键取舍，前端也需要知道，因为它们直接决定接口形态和延迟曲线：

1. **架构为推理成本服务。** Hy4 flash 引入混合 SWA，把 KV cache 压到原来的 1/4；Engram 参数可卸载到主机内存。目标是降低服务成本、提高吞吐。
2. **激活参数就是计算预算。** 团队明确说，减少激活参数"最终意味着更少的计算量和更弱的模型"；过度稀疏的 MoE 对推理不友好。
3. **端侧是另一套设计。** 端侧模型会与边缘 GPU 做协同设计；约 3B 激活参数已能胜任图像、UI 截图、图表的理解与推理（不只是 OCR）。

## 二、对前端的指导

### 2.1 过度思考是产品问题，不只是模型问题

模型把 CoT 拉长，用户看到的是**首字延迟变长、输出变慢、成本变高**。前端不能只做"等"，要把过程变成体验：

- **思考过程可折叠、可跳过。** 默认收起，展示"已思考 12s / 3 步"，展开才看细节；不要让思考链挤占正文首屏。
- **区分"在思考"和"卡住了"。** 有心跳/进度/阶段提示（检索 → 推理 → 生成），超过阈值就允许用户打断并要一个"直接给结论"的快速回答。
- **给用户"快/慢"档位。** 对应 flash 与旗舰模型的两级路由：日常问答走快模型，复杂任务显式切换，并在 UI 上标注预计耗时。
- **结论先行。** 流式输出时先给结论段落，再补推导，避免用户被长 CoT 拖住。

### 2.2 延迟与成本：前端要参与路由决策

文章里"1/20 成本"和"KV cache 1/4"这些数字，落到前端就是三件事：

- **请求分级。** 短问答、分类、文案润色、简单 agent 步骤走小模型；代码重构、长链路规划走大模型。分级逻辑应可配置、可灰度、可回滚。
- **上下文预算可视化。** 长上下文跟踪是最先退化的能力之一，前端要把"上下文已用 x%、已压缩历史 y 轮"显式展示，避免用户以为模型还记得。
- **失败降级有据可依。** 大模型超时/限流时自动降级到 flash，并在界面标注"已切换至快速模式"，不要让用户面对一个静默变差的答案。

### 2.3 工具调用：前端是可靠性的最后一道闸

团队承认工具调用准确性靠"高难度样本 + 细粒度奖励"堆积，并且减少激活参数时**工具调用可靠性最先退化**。这意味着前端必须假设它会错：

- **结构化校验前置。** 命令、参数、JSON 在前端（或 BFF）先做 schema 校验，语法不合规不发给执行层，直接回灌一次修正。
- **副作用操作二次确认。** 删除、写库、发包、部署这类动作，一律展示"将要执行什么"再放行。
- **可归因的失败态。** 每次工具调用展示入参、耗时、原始返回、重试次数；失败要能一键重放，而不是让用户重头再来。
- **流式 CLI / Agent 循环要有刹车。** 长时程任务提供暂停、终止、步数上限，并把每一步落成可回看的时间线。

### 2.4 评测：别用已经饱和的分数做前端验收

团队明确表示老基准"分数已饱和"，改看 Agents' Last Exam、ProgramBench 这类新基准。前端同理：

- **验收用真实任务，不用 Demo。** 拿真实用户会话回放，而不是挑 3~5 个好看的 case。
- **建立前端侧的对照实验。** 同一批任务跑两套交互（如"结论先行"vs"全量流式"），用首字延迟、完成率、打断率、二次追问率来判定，而不是个人体感。
- **把指标和"AI 效果"挂钩。** 对话轮次、停留时长这类传统指标在对话式产品里是失真的——聊了十几轮可能是不满意。
- **灰度 + 影子流量。** 新模型/新交互先跑影子或小流量比对，主链路行为等价再放量。

### 2.5 本地与端侧：前端要能吃下"跑在用户机器上"

- 96GB 显存 + 128GB 内存可跑 flash（权重与注意力放 GPU，专家层与 Engram 表卸载到内存）。前端需要**硬件能力探测 + 配置引导 + 显存占用提示**，而不是等用户报错。
- 端侧视觉理解（UI 截图、图表、文档）在 3B 激活量级已可用，可以做离线场景：本地截图提问、无网环境下的文档理解。
- 本地模型意味着**版本碎片化**：前端要做能力协商（capability negotiation），按模型实际支持的功能开/关入口，而不是假设"都有"。

### 2.6 体验边界与安全

- 团队承认"过度拒绝"仍需改善，同时过滤了偏攻击性的安全数据。前端不要把拒绝渲染成"你做错了"：给出**为什么被拒 + 可以怎么改写 + 申诉/换模型入口**。
- 面向开发者场景（渗透测试、逆向、漏洞分析）存在大量攻防双用途请求，产品需要区分"防御性用途"的引导文案，避免一刀切阻断。
- 安全能力展示要克制：团队自己说"漏洞发现强、漏洞利用弱"，前端文案不要替模型过度承诺。

### 2.7 写作与可读性：别让模型把界面写丑

团队把创意写作与可读性列为重点改进方向，也承认"有时候一个好例子比五段文字更有帮助"。前端能做的是：

- 排版兜底：长文本的段落节奏、列表、代码块、表格渲染质量，比多写 200 字更能提升观感。
- 默认结构化：优先卡片 / 步骤 / 对比表，而不是一大段散文。
- 可编辑：生成后的文本要能就地改，改完能继续追问，而不是复制走人。

## 三、可直接落地的检查清单

- [ ] 思考过程折叠 + 阶段进度 + 可打断，超时降级为"直接给结论"
- [ ] 模型分级路由表（快 / 旗舰），UI 标注模式与预计耗时
- [ ] 上下文占用与压缩历史可视化
- [ ] 工具调用 schema 前置校验 + 副作用二次确认 + 失败可重放
- [ ] Agent 长任务支持暂停 / 终止 / 步数上限 / 时间线回看
- [ ] 前端评测基于真实会话回放，跑对照实验而非单点 Demo
- [ ] 新模型先影子流量比对，再灰度放量
- [ ] 本地/端侧能力探测、显存提示、capability negotiation
- [ ] 拒绝态文案包含原因、改写建议、替代路径
- [ ] 长文本默认结构化输出 + 可编辑

---

## 四、一句话结论

对前端来说，这篇文章的落点不是"模型更强了"，而是：**当模型开始"想太多"、能力分层、还能跑在用户机器上时，前端的核心工作是把不确定的推理过程变成可等待、可打断、可验证、可回滚的界面。**
